# 案例研究：先規則、後 LLM——如何在健康解讀中安全地用 AI

> ClinCalc 的核心設計決策，以及它為什麼能同時降低幻覺與隱私風險。

## 一句話

我沒有把使用者的原始檢驗數值丟給 AI，而是**先在瀏覽器本地用知識庫判定**出「正常 / 偏高 / 偏低」，**只把結構化的判定結果**交給 Gemini 做整體建議。這一個順序的差別，同時解決了**幻覺**與**隱私**兩個問題。

---

## 1. 問題

民眾拿到體檢報告看不懂，最直覺的做法是把數值貼給 ChatGPT 問。但這有兩個結構性問題：

1. **隱私**——把檢驗數值上傳給第三方 AI，資料就離開了你的掌控。
2. **幻覺**——LLM 要「記住」每個指標的正常範圍（而且男女、年齡還不同），一旦記錯，判讀就錯，而且**你無從察覺**。

## 2. 決策：把「判定」與「生成」分開

我把流程拆成兩段，中間用一層結構化的判定隔開：

```
使用者填 35 項指標
      │  ← 原始數值到此為止，不再往後傳
      ▼
本地知識庫 referenceRanges.ts   （KDIGO 2024 / ADA / ACC-AHA）
      │  男女參考區間、單位、來源指引
      ▼
checkAbnormal() → 正常 / 偏高 / 偏低 / 嚴重偏高 / 嚴重偏低
      │  ← 只有這個「結構化判定」往後傳
      ▼
組 prompt 交給 Gemini → 整體評估、生活建議、就醫時程
```

**關鍵**：LLM 收到的不是「LDL = 165 mg/dL」，而是「LDL：偏高」。所以——

- **隱私**：原始數值在本地判定後就停住，不離開瀏覽器。
- **幻覺**：LLM 不需要記憶正常範圍（那是知識庫的工作），它只在**已判定好**的結果上做整體性表達。判讀的正確性由**規則保證、可追溯到來源指引**，不是 AI 憑空生成。

## 3. 為什麼這個順序重要

同樣是「用 AI 解讀報告」，順序決定了信任邊界：

| | 先 LLM（常見做法） | 先規則後 LLM（本專案） |
|---|---|---|
| 誰決定「正常範圍」 | LLM 的記憶（可能錯） | 知識庫（可追溯 KDIGO/ADA） |
| 原始數值 | 上傳給第三方 | 留在本地 |
| 判讀錯了 | 難察覺 | 對得回來源指引 |
| LLM 的角色 | 判定 + 生成（責任過重） | 只做生成（責任明確） |

我把 LLM 從「判斷者」降級成「表達者」——**讓它做它擅長的（把結構化資訊講成人話），不讓它做它不可靠的（記憶精確數值）。**

## 4. 取捨（誠實說限制）

這個策略在**有明確規則**的場景很漂亮（單一指標判定、KDIGO 分期），但也有邊界：

- **綜合判斷**——「整份報告整體看起來如何」這種本質模糊的問題，規則引擎覆蓋不足，還是得靠 LLM，可信度就下降。
- **知識庫維護成本**——KDIGO 每幾年更新一次分期邊界，規則要手動跟著改。
- **症狀↔診斷**這類開放領域（互動式身體地圖），規則能做的有限。

所以這不是「規則萬能」，而是「**能用規則的地方就別讓 LLM 猜**」。

## 5. 實作重點

- 知識庫 [`src/lib/referenceRanges.ts`](../src/lib/referenceRanges.ts)：35 項指標，含中英名、單位、男女參考區間、健康解讀、來源指引。
- 本地判定 [`src/lib/localAnalysis.ts`](../src/lib/localAnalysis.ts)：`checkAbnormal()`。
- KDIGO 2024 慢性腎臟病分期實作到 G1–G5（含 G3a/G3b，共六分期）。
- AI 呼叫一律經後端代理，金鑰不落前端。

## 6. 我從中看到的研究問題

「先規則後 LLM」在清楚的場景好用，但**規則與 LLM 的介入比例到底怎麼分、怎麼量化評估**，我沒有系統性的答案。這讓我想問：

> **能不能設計一套「分級介入」架構——依任務的模糊程度，動態決定規則與 LLM 的比重，並量化評估其幻覺率與覆蓋率的取捨？** 進一步，能不能用 RAG 把臨床指引當動態知識庫，讓系統自動跟上指引改版？

這是我想在碩士階段延伸的方向：把「AI 安全嵌入醫療流程」從個案經驗，變成可量化、可設計的方法。
